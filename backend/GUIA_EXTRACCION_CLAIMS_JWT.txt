===============================================================
  GUÍA: CÓMO EXTRAER INFORMACIÓN DEL TOKEN JWT EN UN ENDPOINT
===============================================================

Esta guía es específica para la arquitectura de este proyecto (IntraNET Bixa).


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  1. QUÉ CLAIMS ESTÁN GUARDADOS EN EL TOKEN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Cuando el usuario hace login, el sistema crea el JWT con estos claims
(ver: backend/Bixa.Backend.Services/Services/JwtControllers/ManejoJwt.cs):

  Claim "Nombre"  → Nombre completo del usuario        (authToken.Name)
  Claim "ci"      → Cédula de identidad / TaxId         (authToken.Ci)
  Claim "id"      → ID numérico del usuario en la BD    (authToken.Id)
  Claim "Rol"     → Nombre del rol (ej: "Empleado")     (authToken.RolName)
  Claim "RolId"   → ID del rol                          (authToken.RolId)

Estos son los únicos datos disponibles para extraer. No hay más.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  2. LAS DOS FORMAS DE EXTRAER CLAIMS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

──────────────────────────────────────────────────
  FORMA A: Directo desde el controlador (con User)
──────────────────────────────────────────────────

Dentro de cualquier método de un controlador que herede de BaseApiController,
puedes acceder a la propiedad `User` (tipo ClaimsPrincipal) que ASP.NET
llena automáticamente con los claims del token cuando el usuario está autenticado.

  // Extraer el ID del usuario:
  var userIdStr = User.FindFirst("id")?.Value;       // devuelve "42" (string)
  int.TryParse(userIdStr, out var userId);            // convierte a int

  // Extraer la cédula:
  var ci = User.FindFirst("ci")?.Value;

  // Extraer el nombre:
  var nombre = User.FindFirst("Nombre")?.Value;

  // Extraer el rol (como string):
  var rol = User.FindFirst("Rol")?.Value;             // ej: "Empleado"

  // Verificar si tiene un rol específico:
  bool esAdmin = User.IsInRole("SuperIntendente");    // true/false

Nota: User es nulo si el endpoint no tiene [Authorize] o si el token
no llegó / expiró. Siempre valida con ?. antes de usar el valor.


──────────────────────────────────────────────────
  FORMA B: Inyectando IJwtAuthService (recomendada
           cuando lo necesitas en un servicio)
──────────────────────────────────────────────────

El proyecto ya tiene JwtAuthService (ver: backend/Bixa.Backend/Base/JwtAuthService.cs)
con métodos listos para usar. Puedes inyectarlo donde necesites:

  // En el constructor del controlador o servicio:
  private readonly IJwtAuthService _jwtAuthService;

  public MiController(..., IJwtAuthService jwtAuthService) : base(...)
  {
      _jwtAuthService = jwtAuthService;
  }

  // Dentro del método del endpoint:
  int? userId  = _jwtAuthService.GetUserId();           // ID numérico del usuario
  var roleInfo = _jwtAuthService.GetScopedRoleInfo();   // (UserRolEnum, int? userId)

  3. EJEMPLO COMPLETO: GET api/usersProfit
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Supón que quieres que el endpoint devuelva solo los datos del usuario
que está haciendo la llamada (identificado por su token).

  [HttpGet("usersProfit")]
  [Authorize]
  public async Task<IActionResult> GetUsersProfit()
  {
      // 1. Verificar rol si es necesario (opcional)
      var authResult = RequireUserRol(UserRolEnum.Empleado, UserRolEnum.SuperIntendente);
      if (authResult != null) return authResult;

      // 2. Extraer el ID del usuario desde el token (Forma A)
      var userIdStr = User.FindFirst("id")?.Value;
      if (!int.TryParse(userIdStr, out var userId))
          return HandleServiceResult(Result.Fail("Token inválido: no contiene ID de usuario.", ErrorTypeEnum.Unauthorized));

      // 3. Extraer otros datos si los necesitas
      var ci     = User.FindFirst("ci")?.Value;
      var nombre = User.FindFirst("Nombre")?.Value;
      var rol    = User.FindFirst("Rol")?.Value;

      // 4. Usar el userId para llamar al servicio
      var result = await _miServicio.GetProfitByUserAsync(userId);
      return HandleServiceResult(result);
  }

  4. FLUJO INTERNO: POR QUÉ FUNCIONA AUTOMÁTICAMENTE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Request HTTP (con header: Authorization: Bearer <token>)
       │
       ▼
  Middleware de ASP.NET (JwtBearer configurado en Program.cs)
       │  → Valida la firma, expiración, issuer y audience
       │  → Si es válido, deserializa los claims del JWT
       │  → Llena HttpContext.User con esos claims
       ▼
  Tu controlador recibe la request
       │
       ▼
  User.FindFirst("id") → Accede a los claims ya hidratados
                          sin necesidad de leer el token tú mismo

  5. CUÁNDO USAR CADA FORMA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Situación                                    Forma recomendada
  ─────────────────────────────────────────    ──────────────────
  Dentro de un controlador                  →  Forma A  (User.FindFirst)
  Dentro de un servicio (sin HttpContext)   →  Forma B  (IJwtAuthService)
  Necesitas el userId como int              →  _jwtAuthService.GetUserId()
  Necesitas verificar el rol               →  User.IsInRole() o RequireUserRol()
  Necesitas rol + userId juntos            →  _jwtAuthService.GetScopedRoleInfo()
